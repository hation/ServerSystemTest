## 2.5 时间锚点（更正：仍不可判定）

初版把 `monitor.csv` 的 Windows 修改时间当作"拷贝时刻"，得出"末采样距拷贝 ≤1 秒 → 当时仍在运行"。**该推论已作废**，理由如下：

1. 同一容器内不同文件的 mtime 各不相同（以 `stress-test-2` 为例：`info-before.txt` 为 02:34、`operations.log` 为 03:26、`monitor.csv` 为 08:19），说明 mtime 是**源文件写入时间被保留**，不是统一的拷贝时刻。
2. 因此 mtime 与日志时间只反映两件事：文件何时被写、以及写入时系统时钟读作几点。
3. 分组差异依然成立：A 组（10 个）mtime 与日志时间一致；B 组（10 个）mtime 比日志时间**早整 8 小时**，说明 **B 组机器的系统时钟比真实时间快 8 小时**。
4. 由于无法从快照确定"拷贝发生在何时"，也就无法判断末次采样之后进程是否还在跑。

结论：`RUNNING` 仍为 **0**，23 个会话维持 `UNKNOWN`；绝对时间锚点必须由现场 `date; timedatectl` 提供。

## 6. 确定的事实

1. 157/157 批次无 `*.exitcode`（全目录 `*exit*` 匹配为 0）。
2. 157/157 的 `stress*.log` 无 `run completed` 收尾行。
3. 151 个批次有 `error*.log` 且最大 74 字节（仅表头）；6 个 11-13 旧批次无 `error.log`。
4. 覆盖率 0.5%~49.9%，无一场接近计划结束。
5. 20 个会话为混合模式，11 个为单一类型（8 个是 1.9% 以下短跑）。
6. 内存规格：994Gi（49 批）、1126Gi（98 批）、754Gi（10 批）；mem 预设固定 864G。
7. `stress-test-20` 期间 swap 打满（4183140 kB ≈ 4Gi）。
8. 6 个 11-13 批次超时为 12h，其余 10h。

## 7. 不得下的结论

- 不得说"通过 / 跑完"：无退出码、无收尾行、未达计划结束。
- 不得给单项数字（单盘吞吐、单类型 CPU 达标率）；混合模式只给整机聚合口径。
- 但**不得因混合判不合格**——混合是设计形态。
- 不得说"所有盘都测过"：8 个会话存在缺测/超测。
- 不得说"设备没问题"：`error.log` 只覆盖 OOM 关键字，内核/硬件错误存在采集盲区。

## 8. 收敛到 OK 还缺什么

| 需要 | 用途 |
|---|---|
| 现场 `date; date -u; timedatectl` | 建立时间锚点，启用 B3 |
| 拷贝时刻（本机时间） | 区分 `RUNNING` / `ABORTED` |
| `pgrep -a stress` + `readlink /proc/<pid>/cwd` | 确认活着、确认压的哪块盘 |
| `df -h / /mnt/HDD*` | 确认挂载、确认是否写根分区 |
| `dmesg -T` + `smartctl` | 补内核与盘健康证据 |
| 跑满 10h 且 `exitcode=0` 的混合批次 | 唯一能产出 `OK` 的形态 |

> 采集命令见方案 8.2 节，整段复制即可执行。

## 9. 局限

- ABORTED 依赖"同容器同一时钟"假设。
- 会话归并 120s、强制分割按挂载数变化，均为代理指标。
- 覆盖率用采样首末差估算，monitor 先退出会低估。
- 无拷贝时刻与现场信息，`RUNNING` 为 0，不代表没有任务在跑。
- 内存达成判据用"目标 864G 的 90%"，对 754Gi 机型物理不可达，应视为配置问题而非设备问题。
