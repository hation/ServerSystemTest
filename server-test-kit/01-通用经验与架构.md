# 01 · 通用经验与架构 —— 测试类项目经验沉淀与新项目复用指南

> **目的**：把测试类工具项目（如硬盘压测、DDR5 内存压测等）从零到平台的全过程经验，沉淀成**新项目开工前必读的清单**——继承什么、规避什么、提前规划什么、怎么跑得又快又稳。
> **状态**：[当前有效]
> **变更记录**：来源 `disk-tests/docs/29-disk-tests经验沉淀与新项目复用指南.md`（去业务化泛化 + 新增双项目共性基因小节）。

## 1. 演进回顾：为什么能从"一个脚本"长成"一个平台"

| 阶段 | 做了什么 | 关键收获 |
|---|---|---|
| v1 | Linux bash 一键脚本（run_xxx.sh + lib_common.sh） | 先解决"有没有"，一条命令跑通 |
| v2 | 分级测试 + 损耗控制（销售场景需求驱动） | **需求驱动迭代**，功能跟着业务走 |
| v3 | Windows 化（run_level1.ps1 等） | 平台扩展，业务逻辑与平台解耦 |
| v4 | WPF GUI（Gui + Core 两层） | 从脚本到"产品"，GUI 只是壳 |
| v5 | SQLite 历史库（db_* 脚本） | 测试数据从"批次孤岛"变成"可追踪资产" |
| v6 | 专项工具（run_erase / run_reset 类） | 新增功能直接复用既有基建，几天交付 |

**第一条经验：演进式构建，架构骨架一次定型，功能沿骨架长。**
每一步都踩在上一版验证过的架构上，没有推倒重来。新项目不要从零设计"完美架构"，而是先定一个**能长后续功能的骨架**，然后让需求驱动生长。

## 2. 值得继承的优点（新项目直接复用）

| # | 优点 | 为什么有效 | 出处 |
|---|---|---|---|
| 1 | **四层架构**：薄GUI → Core → 脚本 → 标准工具 | 标准工具打底 → 结论可审计可解释；GUI 只是壳，重活都在脚本层 | src/Gui + Core + bin/*.ps1 |
| 2 | **防呆**：排除高危目标/打印清单二次确认/破坏操作强确认/`-DryRun` | 高危操作的安全网，客户敢让你测 | lib_common.ps1 Get-TestTargets、Confirm-Targets |
| 3 | **断点续跑 + 幂等**（每阶段落 `.done` 标记） | 几小时的测试中断不白跑，重跑自动跳过 | lib_common.ps1 Get/Set-StageDone |
| 4 | **SQLite 历史库三段式**（批次/实体/测试记录）+ 导出合并 | 跨批次按唯一键追踪同一被测实体，"病历本"是最强差异化 | db_common.py 等脚本 |
| 5 | **任务清单**（测试前计划、测完填结果） | 过程透明、结果可解释，不懂技术也能看懂 | New/Update-TaskChecklist |
| 6 | **报表三件套**（明细CSV + 汇总 + 简表），判定规则写死 | 结论可审计，任何一条都能翻出证据 | merge_results.py → report_detail.csv |
| 7 | **配置驱动 conf + GUI 配置页**（修改即生效） | 调参数不改代码不重启 | conf/app.conf + ConfEditor |
| 8 | **版本号机制**（每版递增，报告可追溯） | 拷贝到目标环境能确认是否最新版 | lib_common.ps1 Get-AppVersion |
| 9 | **确定性抽样**（唯一键 hash） | 同一被测实体结果稳定，复测可对比 | Get-SnHash01 |
| 10 | **系统级证据采集**（系统事件/错误事件窗口） | 硬件故障的系统证据不遗漏 | Get-SystemEvents |
| 11 | **文档体系**（方案/手册/部署清单/对比/产品介绍） | 数十份文档 = 知识资产，新项目直接套模板 | docs/ 编号文档 |
| 12 | **离线绿色目录**（免安装免联网，拷贝即用） | 目标机房经常没网 | build.ps1 出离线包 |

> 复用的正确姿势：**不是"参考"，是"抄骨架改字段"**。例如历史库脚本改名复用、任务清单模板直接改环节名。

## 3. 踩过的坑与不足（新项目第一天就规避）

| # | 坑 | 当时的代价 | 新项目做法 |
|---|---|---|---|
| 1 | **没有自动化测试框架**，靠手工夹具验证 | 连续修多个 bug（统计误报/内联 if/编码/重置逻辑），改一处坏一处 | **第 1 天建 tests/**：解析器 pytest、判定/报表造假产物断言、参数构建断言命令拼接 |
| 2 | **bin 与 deploy/bin 双目录**，靠人肉同步 | 版本漂移（v23 vs v21），拷错版本排查半天 | **单源构建**：build.ps1 一键生成离线包，删掉手工 deploy 目录 |
| 3 | **同一逻辑在两处实现**，靠注释"保持同步" | 改一处漏另一处，行为不一致 | 同一逻辑只实现一次（模块引用 + 单测兜底） |
| 4 | **GUI 单文件过载**（MainWindow.xaml.cs 783 行） | 改一处牵连六处，难维护 | 按功能拆文件/拆 VM |
| 5 | **进度靠轮询 .done 文件猜测** | 高级别进度提前到 100%，不准 | 脚本输出**结构化 JSON 事件行**，GUI 解析，进度精确 |
| 6 | **文档无生命周期**（多份无法判断过时） | 新旧文档冲突，误导 | 每份文档标 [当前有效]/[已废弃] |
| 7 | **真实硬件验证滞后**（多处"需真机验证"） | 部署到真机才发现问题，返工 | 里程碑内置**真机冒烟门禁** |
| 8 | **版本单一来源缺失**（脚本/GUI/deploy 各写各的） | 版本对不上，难以定位 | 版本只定义一处，构建时注入 |

> **最痛的教训**：第 1 条。功能越做越多，没有回归测试就靠"上次能跑"，这是 bug 反复出现的根因。新项目测试框架的优先级要高于任何单个功能。

## 4. 新项目开工前的规划框架

### 4.1 架构模板（直接抄，改 `<project>` 命名）

```
GUI（薄，只做展示/交互）───> Core（进程管理/参数构建/事件解析，可单测）───> 业务脚本（并发/防呆/断点/清单）
───> 标准工具（业界标准，结论可审计）───> SQLite 历史库 + CSV/清单报告
```

各层以 `<project>` 前缀命名：`src/<project>Gui`、`src/<project>Gui.Core`、`bin/run_<project>.ps1` 等。

### 4.2 业务设计 checklist（开工前答完这 10 问，答不完不开工）

| # | 问题 | 为什么必须答 | 整机测试参考（示例） |
|---|---|---|---|
| 1 | **被测实体的唯一键是什么？** | 决定历史库怎么归并、跨批次怎么追踪 | 资产号/SN（无则兜底 Asset_<n>） |
| 2 | **防呆边界在哪？哪些绝对不能碰？** | 高危操作的安全网，客户信任的底线 | 排除生产在用机 + 二次确认 |
| 3 | **测试怎么分级？**（快/标准/深度） | 兼顾效率与可信度，销售场景降损耗 | quick / standard / deep + 抽样深测 |
| 4 | **判定规则能否写死？** | 结论必须可复核、可解释 | 规则表 + 达标线 conf 化（PASS/WARN/FAIL） |
| 5 | **报告给谁看？**（客户/领导/操作员） | 决定报告的字段与口气 | 明细总表 + 大白话清单 + 任务清单 |
| 6 | **要不要历史库？** | 跨批次追踪是最强差异化，但要成本 | 要，SQLite 三段式 |
| 7 | **破坏性操作怎么确认？** | 防误操作的硬要求 | 强确认框 + `-DryRun` |
| 8 | **要不要断点续跑？** | 长耗时测试中断的兜底 | 要，`.done` 标记 |
| 9 | **并发模型？** | 决定脚本骨架 | 并发槽位 Wait-Slot + conf 并发数 |
| 10 | **平台范围？** | 决定执行层技术栈 | Windows 优先，Linux 预留 |

### 4.3 工程基建（第 1 天就建，不是最后补）

1. 自动化测试框架（最优先，见 §3-1）
2. 单源构建（build.ps1 出离线包）
3. 结构化事件流协议（脚本→GUI）
4. 版本单一来源
5. 文档模板 + [当前有效] 标记

## 5. 工作流经验（superpowers 流程怎么用最省时间）

| 环节 | 经验 | 实证 |
|---|---|---|
| **brainstorming** | 先拍板关键决策再动笔，最省时间的是"对话拍板" | 历史库设计时先确认"用途/部署/查询入口"5 个决策，后面没返工 |
| **spec** | 不必过细，覆盖"决策+数据模型+边界"即可 | 数据库 spec 定了三段式模型，实现一次通过 |
| **plan** | 要可执行：每任务含完整代码、验证命令、提交信息 | 计划写完直接子代理驱动，无阻塞连续跑 |
| **执行** | 子代理驱动，主 agent 只审查产物，不停下来等确认 | 多个 plan 连续交付 |
| **文档** | 文档即沟通，先写功能说明再写代码，最后补使用手册 | 每份文档、每个功能都有说明文档 |

> 最省时间的三个动作：**① 开工前把 checklist（§4.2）答完；② 每个功能先写功能说明文档；③ 计划写完直接执行不问执行方式。**

## 6. 给新项目的 10 条启动建议（按优先级）

1. **第一天建自动化测试框架**（§3-1 的教训）
2. **先调研底层标准工具**（能用的标准工具先选定型，不自己造轮子）
3. **真机冒烟前置**（硬件类项目第 0 阶段就安排真机，不闭门开发）
4. **先 CLI 后 GUI**（脚本先把业务跑通，GUI 最后包壳）
5. **报告模板先定**（对外交付核心，字段/判定规则开工前定死）
6. **数据模型先定**（历史库三段式改字段复用，别后补）
7. **单源构建**（删双目录，build.ps1 出离线包）
8. **结构化事件流**（脚本输出 JSON 事件，GUI 解析，进度精确）
9. **版本单一来源**（构建时注入）
10. **文档从第一天写**（每个功能先写说明文档再写代码）

## 7. 双项目共性基因：disk-tests 与 memory-tests 实证的通用架构

disk-tests 与 memory-tests 两个项目**独立开发、业务完全不同**，却不约而同长出了同一套工程基因：

| 基因 | 两项目实证 | 通用化说明 |
|---|---|---|
| **lib_common.ps1 通用函数集** | 防呆/并发槽位/断点续跑/日志/版本/事件输出集中在共享库 | 骨架函数名可直接抄（见 06-工程基建规格 §3.6） |
| **conf 配置驱动** | 键值注释格式 conf + GUI 配置页，修改即生效 | 业务参数用占位键，不改代码不重启 |
| **VERSION 单源 + build.ps1** | 版本只定义一处，构建时注入并出离线包 | 收敛为单点，杜绝版本漂移 |
| **tests 自动化测试** | tests/ 覆盖共享库/参数校验/历史库 | 测试框架优先级高于任何单个功能 |
| **db SQLite 三段式** | 批次/实体/测试记录，导入导出合并幂等 | 跨批次按唯一键追踪被测实体 |
| **JSON 事件流** | 脚本一行一个 JSON 事件，GUI/日志消费 | 进度与状态全部来自事件流，不轮询文件 |
| **AGENTS.md superpowers 规则** | 两项目 AGENTS.md 几乎同文：brainstorming→specs→plans→subagent 执行 | 直接复用，见 07-工作流规则 |
| **离线包模式** | 免安装免联网绿色目录，拷贝即用 | 构建生成，不维护手工 deploy 目录 |
| **指令记录 cmdlog** | 所有脚本自动写 commands-<日期>.csv，密码打码 | 排查历史操作先看这里 |

**结论**：两项目各自独立验证了同一套通用架构——这不是巧合，而是这套骨架对"测试类工具"问题的稳定答案。新项目**直接抄骨架**，只替换业务实体（被测实体=服务器/整机）、唯一键与判定的具体字段。

## 8. 一句话总结

**成功 = 标准工具打底的架构 + 防呆/断点/幂等/入库这些工程基因 + 文档驱动的工作流；教训 = 没有回归测试。新项目：继承基因，第一天补上测试，开工前答完 10 问。**
