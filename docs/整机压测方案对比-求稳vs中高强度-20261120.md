# 整机压测方案对比：求稳档 vs 中高强度档（2026-11-20）

> 视角：**整机**——CPU + 内存 + 全部硬盘并发（不是纯 CPU+内存）。
> 基准机器：2×海光 C86 5380（32 物理核 / 64 逻辑线程，SMT 开）、内存 12×32G = 384G、14 数据盘 + 系统盘（盘流 peer = 15）。

**核心结论（先行）**：整机场景下，脚本自动推导的"求稳档"（oneclick `all`）内存强度只有 **48%**（被 `cap_disk` 显式预留盘流页缓存所致），内存子系统并未压到位；真正把内存压到接近极限的是中高强度档（oneclick `full`，**75%**）。若整机验收包含内存稳定性验证，`full` 才是正确的档位；`all` 更适合纯 CPU+内存或保守批次。

---

## 1. 对比前提

| 项 | 说明 |
| --- | --- |
| 机器 | 同一台：2×海光 C86 5380，32 物理核 / 64 逻辑线程（SMT 开）；内存 12×32G = 384G（MemTotal 按 ~372G 估算，**以实测为准**）；2×480G 系统盘 + 12×8TB + 2×1.92TB NVMe = 14 数据盘 + 系统盘 |
| "整机"定义 | CPU + 内存 + **全部硬盘并发**：COMBO（CPU+内存组合任务）与 14×数据盘 HDDxx + 系统盘 SYSDISK 同时运行；盘流 peer = 数据盘数 + 1 = 15 |
| 求稳档 | oneclick `all`：COMBO 参数由脚本**自动推导**（CPU 唯一公式 + 内存三道上限取最小） |
| 中高档 | oneclick `full`：COMBO 默认按**朋友规则**推导（CPU≈round(逻辑线程×70%)、VM=DIMM 根数、vm-bytes=脚本单根推导 单条容量−max(单条/8,6G)，推导值作为显式参数写入、**不走自动推导/裁剪**）；`FULL_*` 显式设置可覆盖（显式优先，未设置项由推导补齐），如"朋友方案" FULL_CPU=45 / FULL_VM=12 / FULL_VMBYTES=24G |
| 超时 | 两方案默认一致：`--timeout` 默认 10h（`DEFAULT_TIMEOUT=10h`），可覆盖 |
| 数据盘任务 | 两方案一致：每块数据盘独立 `HDDxx` 任务，`--hdd-bytes` 默认 10G；系统盘 SYSDISK 同规格 |

参数口径要点：**求稳 = 脚本自动推导（all）**，**中高 = full**——默认按**朋友规则**推导（CPU≈round(逻辑线程×70%)=45、VM=DIMM 根数=12、vm-bytes=脚本单根推导 单条容量−max(单条/8,6G)=32−max(4,6)=26G，推导值显式下发、不裁剪）；显式设置 `FULL_*` 时用所给值（如朋友方案 45/12/24G，`FULL_*` 可覆盖）——两者是同一套编排框架（全盘挂载 + COMBO 先启动 + 每盘 HDDxx + SYSDISK），差别只在 COMBO 的内存/CPU 参数来源（脚本自动推导 vs 朋友规则/显式指定）。

## 2. 两方案参数全景表

| 参数 | 求稳档（all 自动推导） | 中高档（full：默认朋友规则推导，下表为显式 24G 场景） | 差异 |
| --- | --- | --- | --- |
| COMBO CPU worker | `round(64×25/32)` = **50**（≈78%） | FULL_CPU = **45**（≈70%） | 求稳 CPU 反而更高 |
| COMBO 内存条数（VM） | 12（自动按根数） | FULL_VM = **12** | 一致 |
| COMBO 单 worker | **15G**（被 cap_disk 压到） | FULL_VMBYTES = **24G** | 中高为求稳的 1.6 倍 |
| COMBO 内存总量 | 12×15G = **180G** | 12×24G = **288G** | 中高多 108G |
| 内存占比 | 180G / 372G(MemTotal) ≈ **48%** | 288G / 384G(标称) = **75%**（见 §3 口径说明） | 中高明显更高 |
| 数据盘任务 | 14×HDDxx，hdd-bytes 默认 **10G** | 14×HDDxx，hdd-bytes 默认 **10G** | 一致 |
| 系统盘任务 | SYSDISK，hdd-bytes 默认 10G | SYSDISK，hdd-bytes 默认 10G | 一致 |
| 盘流 peer（内存预留口径） | 数据盘数+1 = 15 | 数据盘数+1 = 15 | 一致 |
| 超时 | 默认 10h（`--timeout` 可覆盖） | 默认 10h（`--timeout` 可覆盖） | 一致 |

说明：hdd-bytes=10G 为脚本默认值（两方案一致，未显式调整）；COMBO 的 `--peer-disks 15` 只参与内存预留（`cap_disk`）与展示，不启动 hdd 进程，每块盘由各自 HDDxx 任务压一次。full 默认朋友规则推导为 45/12/**26G**（脚本单根推导 32−max(4,6)=26G，12×26=312G），下表以显式 24G（朋友裸命令口径，12×24=288G）场景列数值，两者均不裁剪。

## 3. 内存账目对比（逐步算式）

### 3.1 求稳档（all）——脚本自动推导，被 cap_disk 显式压低

脚本内存计划对 COMBO 设**三道上限取最小**，然后按根数逐 GiB 下调单 worker：

1. **cap_module（模块总容量上限）** = 模块总容量 × 88%（`MEM_MAX_PCT=88`）
   - 384 × 88% = 337.92 ≈ **338G**
2. **cap_mem（MemTotal 上限）** = MemTotal × 92%（`MEM_TOTAL_MAX_PCT=92`，防 OOM）
   - 372 × 92% = 342.24 ≈ **342G**
3. **cap_disk（盘流页缓存预留）** = MemTotal − (盘流数 × hdd-bytes × 1.2 + 8G)（`DISK_CACHE_FACTOR_PCT=120`、`DISK_CACHE_MIN_G=8`）
   - 15 × 10G × 1.2 = 180G（15 路盘流的页缓存/脏页预留，含系统盘）
   - 372 − (180 + 8) = **184G**

**min(cap_module, cap_mem, cap_disk) = min(338, 342, 184) = 184G** ← 生效的是 cap_disk。

按 12 条内存：184 / 12 = 15.33 → 向下取整到整数 GiB → **单 worker 15G** → 实际下发 12 × 15 = **180G**。

占比口径（MemTotal）：180 / 372 ≈ 48.4% → **≈48%**。

### 3.2 中高档（full）——朋友规则推导，显式下发、脚本不裁剪

full 的 COMBO 参数默认按**朋友规则**推导并作为显式参数下发（CPU≈round(64×70%)=45、VM=DIMM 根数=12、vm-bytes=脚本单根推导 32−max(4,6)=26G），直接下发、不受 cap_disk（184G）约束——这正是 full 与 all 的机制差异：**full 的 COMBO 参数脚本不裁剪**；显式设置 FULL_VMBYTES=24G（朋友方案）时用所给值（12×24=288G），同样不裁剪。以下数值分析以显式 24G 场景为例。

占比口径：288 / 384（标称容量）= **75%**，与 full 菜单设计目标"内存≈75%"一致。若统一按 MemTotal 372G 口径：288 / 372 ≈ **77.4%**——按任一口径，中高内存强度都显著高于求稳。

### 3.3 页缓存余量对比（估算）

整机并发时，COMBO 占用的内存 + 系统常驻之外的部分即页缓存/脏页空间，供 14 路盘写盘周转。

| 项 | 求稳档 | 中高档 |
| --- | --- | --- |
| MemTotal | ~372G（估算，以实测为准） | ~372G |
| COMBO 占用 | 180G | 288G |
| 系统常驻（估算） | ~6G | ~6G |
| **页缓存余量** | 372 − 180 − 6 ≈ **186G** | 372 − 288 − 6 ≈ **78G** |

14 路盘写盘峰值需求（估算上限）：14 × 10G = **~140G**。
- 求稳 186G ≥ 140G：**余量充足**，页缓存完全覆盖盘流峰值，OOM 风险低；
- 中高 78G < 140G：**余量偏紧**，盘流峰值需求超过页缓存余量，靠"页缓存可回收 + SSD（2×1.92TB NVMe）刷盘快"兜底，可运转但需监控（见 §5.3 / §6）。

## 4. CPU 口径对比

| 项 | 求稳档（all） | 中高档（full：默认朋友规则推导 = 45，显式 FULL_CPU 可覆盖） |
| --- | --- | --- |
| CPU worker 公式 | `max(1, round(逻辑线程 × 25/32))` | `round(逻辑线程 × 70%)`（默认推导）；显式 FULL_CPU=45 可覆盖 |
| 算式 | round(64 × 25/32) = round(50) = **50** | round(64×70%) = **45** |
| 占用比例 | 50 / 64 ≈ **78.1% → 78%** | 45 / 64 ≈ **70.3% → 70%** |
| 留给 IO/系统线程 | 64 − 50 = 14 | 64 − 45 = **19（≈30%）** |
| IO 余量意图 | 无——78% 接近饱和，未刻意给 14 路 IO 留余量 | 有——显式留 ~30% 线程给 14 路 IO 并发 |

关键点：**求稳档 CPU 反而更高（78% > 70%）**。整机并发时 14 路盘 + 系统盘的 IO 处理（中断/内核线程/驱动）需要 CPU 线程，求稳档 78% 不给 IO 留余量，IO 处理可能被 CPU 负载抢占；中高档 70% 是"朋友参数"的显式取舍——CPU 略降，为 IO 留 ~19 线程（≈30%）余量。

## 5. 关键差异解读

### 5.1 内存强度：48% vs 75%——"求稳"在整机场景下内存反而测不到位

整机场景下，all 的内存总量被 **cap_disk 显式预留**压低到 180G（48%），原因是脚本要为 15 路盘流预留页缓存（`15×10G×1.2+8G=188G`），宁可内存负载降档也不让盘流缺页缓存。

- 若整机验收**包含内存稳定性验证**：48% 只把内存用到一半不到，内存子系统（控制器、颗粒、ECC、温度）压力不足，**all 测不到位**；
- full 的 288G（75%）才把内存压到接近极限，内存子系统得到有效验证。

**实质结论：整机场景下，"求稳"的 all 在内存上是低强度档（48%），真正把内存压到位的是 full（75%）；full 才是整机中高强度档。**

### 5.2 CPU：求稳 78% 更高，但不给 IO 留余量

- 求稳档 CPU 占用更高（78%），但未给 14 路 IO 留余量——整机并发时 IO 处理可能被抢，存在"CPU 看似压满、盘流 IO 处理不充分"的风险；
- 中高档 70% 为 IO 留 ~30% 线程，CPU 与盘流并发更均衡。

### 5.3 风险与余量

| 项 | 求稳档 | 中高档 |
| --- | --- | --- |
| OOM 风险 | 低（页缓存余量 ~186G，充足） | 偏高（余量 ~78G，盘流峰值 ~140G，需可回收页缓存 + SSD 刷盘兜底） |
| 内存子系统压力 | 不足（48%，测不到位） | 到位（75%） |
| CPU 满载度 | 78%（IO 无余量） | 70%（IO 留 ~30%） |
| 建议监控 | — | `free -h` / `sar -r`（内存与页缓存水位）、`dmesg \| grep -i oom`（OOM 事件） |

## 6. 适用场景与建议

| 场景 | 推荐档位 | 理由 |
| --- | --- | --- |
| 整机验收（含内存稳定性验证） | **full（中高）** | 内存压到 75%，内存子系统验证到位；CPU 70% 为 IO 留余量，整机并发更均衡 |
| 保守批次 / 纯 CPU+内存验证（不含整机盘流） | **all（求稳）** | 内存 48% 低负载、OOM 风险低、余量足；纯 CPU+内存场景下无盘流争抢页缓存，48% 已属合理负载 |
| 需要介于两者之间 | full + 降档覆盖 | 见下 |

**full 的 FULL_* 覆盖说明**：full 的 COMBO 参数默认按朋友规则推导（CPU≈逻辑线程 70%、vm-bytes=脚本单根推导、不裁剪）；显式设置 FULL_* 环境变量可逐项降档/调参，无需改脚本：

- `FULL_CPU=40`：CPU worker 覆盖（未设置则朋友规则推导 45）；
- `FULL_VM=12`：内存条数覆盖（未设置则按 DIMM 根数推导）；
- `FULL_VMBYTES=20G`：单 worker 内存覆盖（未设置则脚本单根推导 26G），**降档路径示例**——12×20G = 240G（240/384 标称口径 ≈ 63%；按 MemTotal≈372G 实测口径为 64.5%），介于 48% 与 75% 之间，页缓存余量回升到 372−240−6 ≈ 126G，兼顾内存强度与盘流安全。

**监控项（中高档必做）**：`free -h`（内存/页缓存水位）、`sar -r`（内存与换页统计）、`dmesg | grep -i oom`（OOM 事件）。若出现 OOM 或页缓存水位持续逼近盘流需求，优先降 `FULL_VMBYTES`（如 20G）而非降 CPU。

**备注**：所有占比/余量为基于 ~372G（MemTotal 估算值）的推算，正式验收前以 `free -m` / `cat /proc/meminfo` 实测为准；系统常驻 ~6G 为估算。
