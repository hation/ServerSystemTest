# stress 工具机制与当前压测方案对比评估

- 评估日期：2026-11-18
- 评估范围：stress 工具机制（多源联网交叉验证）对照当前压测方案（SMT 感知 CPU worker、内存按根数×单条分配、`--vm-keep`、三 cap、hdd 独立进程）
- 文档性质：**供审核决策的对比评估**——只做对照与选项罗列，不含任何代码改动；是否调整由审核决定

## 结论摘要（Executive Summary）

**结论：当前方案能实现压测目的——可达到基本的 burn-in（持续负载下稳定性）效果，无需先做任何调整即可继续使用。**

依据：stress 的工具定位本身就是"施加可配置负载并报告错误"而非 benchmark，与 burn-in 目的（持续压力下观察稳定性、捕获报错）契合 [cite:1][cite:2]；当前方案的 CPU worker、内存占用、`--vm-keep` 常驻、三 cap 兜底均落在 stress 机制允许的正确区间内，不存在机制误用。

**关键 gap（一句话）：** CPU 强度留 22% 余量（78% worker 不打满整机）、内存带宽/控制器压力有限（默认 stride 每 4K 仅写 1 字节，写活动很轻）、内存占用水位 81.25%~87.5% 高于通用负载指导的 70-75%（避免 swap）阈值——三者均属"强度与覆盖"层面的差距，不构成方案不可用。

**建议决策点：** 审核以下三选（详见 §4）：维持现状；纯 CPU 场景提高强度（接近 90% 上限或打满）；内存维度增强（引入 stride 控制或 stress-ng）。是否调整取决于"整机打满峰值"与"留余量协同"两个目标的取舍——本文档不预设结论。

## 1 stress 工具机制（查证）

### 1.1 CPU 与内存机制

| 参数/机制 | 查证行为 | 引用 |
|---|---|---|
| `--cpu N` | 生成 N 个 worker，各自在 `sqrt()` 上自旋（忙循环）；1 个 worker 占满 1 个逻辑线程 | [cite:1][cite:2][cite:5] |
| `--vm N` | 生成 N 个 worker 循环 `malloc()/free()`（默认：分配→触摸→释放→再分配，脉冲式） | [cite:1][cite:2][cite:3] |
| `--vm-bytes B` | **每个** vm worker 分配 B 字节（默认 256MB）；总内存占用 = N × B | [cite:1][cite:2] |
| `--vm-stride B` | 每 B 字节写 1 字节以触发 COW/页面驻留；默认 4096（即每 4K 写 1 字节，写活动很轻） | [cite:2][cite:6] |
| `--vm-hang N` | free 前 sleep N 秒（0 = 无限保持分配） | [cite:2] |
| `--vm-keep` | redirty 内存而非释放重分配 → 内存常驻，是持续压力的关键 | [cite:2][cite:3] |

### 1.2 工具定位与能力边界

- stress 不是 benchmark，而是"施加可配置负载并报告错误"的工具（Amos Waterland 原创）[cite:1][cite:2]；因此其适合 burn-in/稳定性观察，不适合作为性能量化基准。
- 通用负载测试指导：内存占用建议低于 70-75%（避免 swap），CPU 低于 90% [cite:7]。
- stress-ng 是 stress 的增强版：完全兼容 stress 基本参数，另有数十种 stressor（CPU 50+ 类、内存 20+ 类等），可产生更复杂的压力形态 [cite:8][cite:9][cite:10]。

## 2 对照分析表（当前参数 ↔ stress 机制）

| 维度 | 当前方案参数 | stress 机制 | 判定 | 备注 |
|---|---|---|---|---|
| CPU worker | `max(1, round(逻辑线程×25/32))`（SMT 感知：开=2/关=1/未知默认开；物理核识别失败回退 `round(nproc×78%)`）；逻辑线程 = 物理核 × 每核线程数 | 1 worker 占满 1 逻辑线程 [cite:1][cite:2][cite:5] | 符合（机制语义） | 25/32 ≈ 78%，留 22% 余量，不打满整机；强度取舍见 §3.1 |
| VM worker 数 | 内存条根数 | N 个 worker 各自独立 malloc [cite:1][cite:2][cite:3] | 符合 | 根数×单条与"每 worker 一份"机制对应 |
| vm-bytes | 单条容量 − max(6G, 单条/8)（32G→26G、64G→56G） | 每 worker 分配 B 字节，总占用 = N×B [cite:1][cite:2] | 符合 | 总量 = 根数 × (单条 − 预留)，见 §3.2 水位分析 |
| `--vm-keep` | mem/combo 场景固定追加 | redirty 常驻，持续压力关键 [cite:2][cite:3] | 符合（推荐项已用） | 内存"占用+驻留"达标 |
| 三 cap | 模块容量×88%、MemTotal×92%、cap_disk=MemTotal−(盘流×hdd-bytes×1.2+8G)；超限逐 GiB 下调单 worker | 工具本身无内置保护；超订阅会导致 OOM/swap；通用指导内存 <70-75%、CPU <90% [cite:7] | 部分符合 | cap 属机制外主动保护，避免 OOM；但水位高于通用指导阈值，见 §3.2 |
| stride | 未设置（用默认 4096） | 每 4K 写 1 字节，写活动很轻 [cite:2][cite:6] | 符合（默认行为） | 占用高 ≠ 带宽压力大，见 §3.2 |
| hdd | 每盘 1 进程、缓冲写（页缓存注意） | 本次调研事实库未覆盖 stress hdd 类 stressor 的机制细节 | 不判定 | 超出本评估事实库范围，需另行核实；本节 CPU/VM 维度不受影响 |

## 3 差距与风险分析

### 3.1 CPU 强度 78%（留 22% 余量）与"整机 burn-in"目标

- 机制上，打满整机需 worker ≈ 逻辑线程数（HT 开启时为 2×物理核）[cite:1][cite:2][cite:5]；当前 worker = 逻辑线程×78%，即最多 22% 的线程处于空闲。
- 与通用指导对照：CPU 低于 90% 是负载测试建议上限 [cite:7]，78% 在其内——"留余量协同"取向与通用指导一致，且为系统管理/监控进程留出资源。
- 差距判定：若"整机 burn-in"目标指全线程打满的峰值强度，则当前留 22% 余量意味着峰值强度弱于 100% 打满场景；若目标含"留余量协同"（避免把系统压到无响应边缘），则 78% 是符合目标的取值。二者取舍见 §4。

### 3.2 内存："占用+驻留"达标，但带宽压力有限、水位偏高

- 占用达标：`--vm-keep` 使内存常驻 [cite:2][cite:3]，按当前公式计算（如 12×26G/384G≈81.25%、16×56G/1024G=87.5%），各机型内存总占用落在 81.25%~87.5% 区间（88% 为保护性 cap 上限，实算未触及），"高占用+持续驻留"目标达成。
- 风险点一（水位）：81.25%~87.5% 高于通用负载指导的 70-75%（避免 swap）阈值 [cite:7]。方案以 88%/92% cap 兜底避免 OOM，但该水位已进入接近 swap 的风险区，与 CPU"留余量"取向相反（内存反而更激进）。
- 风险点二（带宽）：stride 未设置（默认 4096），即每 4K 仅写 1 字节，写活动很轻 [cite:2][cite:6]——内存"占用高"不等于"带宽/控制器压力大"，当前对内存控制器与带宽的压测强度有限。

### 3.3 工具能力覆盖：stress 基础工具 vs stress-ng

- 若目标仅覆盖 CPU/内存占用/稳定性 burn-in，stress 基础工具够用；其定位"施加负载并报告错误"与 burn-in 契合 [cite:1][cite:2]。
- 若目标含"内存控制器/带宽高压力"或更复杂的组合压力形态，stress 基础工具应力类型有限；stress-ng 完全兼容 stress 基本参数，并提供数十种 stressor（CPU 50+ 类、内存 20+ 类等）[cite:8][cite:9][cite:10]，可作为候选。

### 3.4 结论判定

在"burn-in 稳定性"目标下：**当前方案能用、可达到基本效果**——机制正确、参数合规、有 cap 兜底、内存驻留达标。存在的 gap 为：CPU 峰值强度留 22% 余量（不打满）、内存带宽/控制器压力有限（stride 默认写活动轻）、内存水位高于通用指导 70-75% 阈值。三者均为"强度与覆盖"层级的差距，不构成方案不可用或必须调整。

## 4 可选调整方案（供决策，不改代码）

以下选项互不排斥，是否调整由审核按"整机打满峰值"与"留余量协同"的目标取舍决定。

| 选项 | 内容 | 预期影响 | 实施代价 | 与既定取向关系 |
|---|---|---|---|---|
| A 维持现状 | 不调整参数与工具 | 保持已验证的规则与留余量协同；上述 gap 维持 | 零实施成本 | 完全一致 |
| B 提高纯 CPU 场景强度 | 将 worker 占比从 78% 上调至接近 90% 上限 [cite:7] 或打满逻辑线程 [cite:1][cite:2][cite:5] | 更接近整机峰值 burn-in；系统管理余量减少 | 需重校准公式与 cap、回归审核（关联既有 R1/R8 规则） | 与"留余量协同"取向冲突，需权衡 |
| C 内存维度增强 | C1 引入 `--vm-stride` 参数控制（如减小 stride 提升写频率与 COW/驻留触发密度）[cite:2][cite:6]；C2 引入 stress-ng 以覆盖更多内存/带宽类 stressor [cite:8][cite:9][cite:10] | 补强内存带宽/控制器压力维度 | 需核实 stride 语义并校准；stress-ng 需离线打包安装；命令与 BOM 变更、行为差异需回归验证 | 在"内存维持默认"取向之外新增控制面 |

说明：C 的两个子选项可独立或组合；B 与 C 可叠加。实施需在审核确认后另行进行（本评估不包含任何代码改动）。
