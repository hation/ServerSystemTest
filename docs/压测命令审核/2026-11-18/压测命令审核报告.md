## 1. 审核范围与方法

### 1.1 审核范围
对 BOM《压测命令》表中 9 行逐行核对：
- CPU worker 数量（`--cpu`）
- VM worker 数量（`--vm`）
- 单 VM 内存大小（`--vm-bytes`）
- 内存总压测占比（`--vm × --vm-bytes` ÷ 系统总内存）
- 内存配置自洽性（总容量 = 根数 × 单条容量）
- 相同硬件规格行之间的参数一致性

### 1.2 规则依据（绑定约束，逐字执行）
| 规则 | 内容 |
|---|---|
| R1 | CPU worker = max(1, round(逻辑线程 × 25/32))（所有机型统一；逻辑线程 = 物理核 × 每核线程数，SMT 探测开=2/关=1/未知默认开） |
| R2 | 物理核识别失败回退 round(nproc × 78%) |
| R3 | VM worker = 内存条根数 |
| R4 | vm-bytes = 单条内存容量 − 6~8G（32G→26G、64G→56G） |
| R5 | 内存总压测目标 = VM worker × vm-bytes，必须 ≤ 88% × 系统总内存 |
| R6 | CPU 型号仅用于交叉校验配置合理性，不得作为压测参数的直接查表依据 |
| R7 | 压测参数必须按服务器实测规格动态生成，禁止硬编码固定值 |
| R8 | SMT 状态参与 CPU worker 分配（方案A）：SMT 开启时 50/75/100；SMT 关闭时按逻辑线程 78.125% 推导（5380→25、7360→38、7380→50）；SMT 探测未知默认按开启 |

### 1.3 逻辑线程数计算约定（按此计算）
2 颗 CPU × 每颗物理核数 × SMT(2线程)：
- 海光 5380（物理核数 16C）→ 2 × 16 × 2 = **64 逻辑线程**
- 海光 7380（物理核数 32C）→ 2 × 32 × 2 = **128 逻辑线程**
- 海光 7360（物理核数 24C）→ 2 × 24 × 2 = **96 逻辑线程**

若实测 SMT 关闭，逻辑线程 = 物理核数（×1），见 1.4 与 6 节。

### 1.4 关键计算值（独立计算，非查表）
- 5380 规则 CPU worker（SMT 开启）：round(64 × 25/32) = round(50.0) = **50**
- 7360 规则 CPU worker（SMT 开启）：round(96 × 25/32) = round(75.0) = **75**
- 7380 规则 CPU worker（SMT 开启）：round(128 × 25/32) = round(100.0) = **100**（统一公式推导，非特殊分支）
- **SMT 关闭时**（逻辑线程 = 物理核 × 1）：5380 → round(32×25/32) = **25**；7360 → round(48×25/32) = **38**；7380 → round(64×25/32) = **50**
- 32G 单条 → vm-bytes = **26G**；64G 单条 → vm-bytes = **56G**

## 4. 5380 专项分析（行 1 --cpu 110 vs 行 5 --cpu 50）

### 4.1 结论
**是问题。** 两台海光 5380 服务器（行 1、行 5）硬件规格完全相同（2 颗 5380，物理核数 16C，SMT 后 64 逻辑线程），但 CPU worker 分别写为 **110** 与 **50**，数值不一致。按最终口径，规则值 = round(64×25/32) = **50**：**行 5 的 50 即规则值（合规）**，**行 1 的 110 是唯一异常**（偏离 60、超过 64 逻辑线程、与行 8 同值疑似复制粘贴）。

### 4.2 哪行异常、依据
- **行 1（--cpu 110）为唯一异常项**：按 R1，5380 规则值为 round(64 × 25/32) = **50**。110 比规则值 50 高出 60，更**超过该机逻辑线程总数 64**——`stress --cpu` 以 worker 进程数压 CPU，110 个 worker 争抢 64 个逻辑线程属于超线程过订阅，压测结果不可解释、无物理意义。同时 110 与行 8（7380 平台）的数值相同，强烈提示为硬编码值被复制粘贴（违反 R7）。
- **行 5（--cpu 50）即规则值（合规）**：规则值 = round(64 × 25/32) = **50**，行 5 现命令 50 与规则值一致，无需修改；与行 1 的 110 形成 110 vs 50 的显著不一致，异常在行 1。

### 4.3 判定依据
- R1（CPU worker = max(1, round(逻辑线程 × 25/32))，SMT 开启下 5380 = 64 逻辑线程）对两台 5380 必须给出**同一**结果 50；
- R7（按实测规格动态生成、禁止硬编码）要求相同硬件 → 相同参数；
- 逻辑线程约定：2 × 16C × 2 = 64（两行共用）。

### 4.4 修正要求
行 1 修正为 `--cpu 50`；行 5 无需修改（已是规则值）：
- 行 1：`stress --cpu 50 --vm 12 --vm-bytes 26G --timeout 10h`
- 行 5：`stress --cpu 50 --vm 16 --vm-bytes 56G --timeout 10h`（合规无需修改）

> 注：以上按 SMT 开启（默认）推导。若实测 SMT 关闭，5380 逻辑线程 = 32（×1），CPU worker 应按 round(32×25/32) = **25** 推导，行 1 与行 5 均改 `--cpu 25`；SMT 关闭数值见第 6 节。

## 7. 并发硬盘压测的参数调整机制（补充说明）

> 适用场景：在"测 CPU + 内存"的同时并行压测数据盘（`oneclick all` 模式）。此时内存分配需为并发盘流预留页缓存，参数由脚本自动调整；本节说明该机制及与本报告单测口径的关系。机制内容核对自 `offline-stress-pkg/stress-test.sh`（`--peer-disks` / `cap_disk` 段）与 `offline-stress-pkg/oneclick.sh`（all 编排）。

### 7.1 并发编排方式（oneclick all）

并发压盘采用 `oneclick all` 模式编排，启动顺序为：

1. **COMBO（CPU + 内存组合任务）**：作为核心负载最先启动，携带 `--peer-disks N`（N = 数据盘数 + 1，固定含系统盘）声明对端并发 hdd 流数；该参数只参与内存预留，**不启动 hdd 进程**（脚本收到 `--peer-disks` 后不再自动扫描 `/mnt/HDD*`，避免 combo 内重复压盘）。
2. **每块数据盘独立终端压测**：每个 `/mnt/HDD*` 目录一个 hdd 任务，各占独立终端窗口。
3. **系统盘独立任务**：`SYSDISK` 以 `--sysdisk-only` 单独压测。

盘流数 = 数据盘数 + 1（含系统盘）；显式 `--peer-disks N` 时有效盘流取 max(实际盘数, N)。COMBO 失败即中止整批；单盘/系统盘启动失败记录后继续其余任务。

### 7.2 CPU 参数不调整

并发压盘场景下 **CPU 参数不调整**，原因：

- CPU worker 仅由逻辑线程决定（SMT 感知公式 R1，本报告 §1.4），与硬盘无关；
- hdd 进程以 IO 等待为主，几乎不占用 CPU 时间，不会与 CPU worker 争抢逻辑线程；
- COMBO 的 `--peer-disks` 只预留页缓存、不启动 hdd 进程（hdd 跑在独立终端），对 CPU 无影响。

因此 §5 修正后的 `--cpu` 值在并发场景下原样保留。

### 7.3 内存参数调整机制

并发场景下内存分配追加"盘流页缓存预留"约束，脚本自动调整，规则如下：

**① 盘流预留（cap_disk）**：

```
cap_disk = MemTotal − (盘流数 × hdd-bytes × 1.2 + 8G)
```

其中盘流数 = 数据盘数 + 1（含系统盘），hdd-bytes 默认 10G，×1.2 为页缓存/脏页冗余、+8G 为系统基础余量。

**② 总目标取三条 cap 最小值**：

```
cap = min(模块总容量 × 88%, MemTotal × 92%, cap_disk)
```

- cap_module = 模块总容量 × 88%（即本报告 §2.2 的 88% 口径）；
- cap_mem = MemTotal × 92%；
- cap_disk = 上述盘流预留后的可用内存。

**③ 单 worker 起始与下调**：

```
单 worker 起始 = 单条容量 − max(6G, 单条容量 / 8)   （与 R4 一致：32G→26G、64G→56G）
若 单worker × 根数 > cap，则逐 GiB 下调单 worker，直到 单worker × 根数 ≤ cap
```

**④ 异常中止**：`cap_disk ≤ 0` 时脚本报错中止，提示"请减少盘数或降低 --hdd-bytes"。

### 7.4 实例（BOM 行 1：5380、384GB/12×32G、12 块数据盘 + 1 系统盘）

以 BOM 行 1（12×32G=384GB、12 块数据盘 + 1 系统盘、hdd-bytes 默认 10G）为例：

- 盘流数 = 12 数据盘 + 1 系统盘 = **13**；
- 盘流预留 = 13 × 10G × 1.2 + 8G = 156G + 8G = **164G**；
- cap_disk = 384 − 164 = **220G**；
- cap_module = 384 × 88% ≈ **338G**（精确 337.92G，即 §2.2 行 1 上限）；cap_mem = 384 × 92% ≈ **353G**（MemTotal 示意值）；
- cap = min(338, 353, 220) ≈ **220G**（cap_disk 为决定性约束）；
- 单 worker 起始 = 32 − max(6G, 32/8=4G) = 32 − 6 = **26G**；12 × 26 = **312G > 220G** → 逐 GiB 下调；
- 下调至 **18G**：12 × 18 = **216G ≤ 220G** ✓；
- 最终内存参数：`--vm 12 --vm-bytes 18G`（起始 26G 下调 8G）；
- **CPU 参数不变**：5380 SMT 开启 64 逻辑线程，`--cpu 50`（同 §5 行 1）。

### 7.5 与本报告的关系（单测口径 vs 并发压盘口径）

- 本报告（§1~§6）审核的是 **单独 CPU + 内存压测** 的命令口径：内存占比按 R5 仅受 `≤ 88% × 系统总内存`（cap_module / cap_mem）约束，§5 修正命令按此核发；
- 采用 `oneclick all` 并发压盘时，内存分配追加 cap_disk 约束，**内存参数由脚本按 §7.3 机制自动调整**（如行 1 由 26G 下调至 18G），**无需手工修改命令**；CPU 参数两类场景一致；
- 两种口径不冲突：单测口径是并发口径的上层子集（并发时 cap 多一条 cap_disk 下限），§2.2 行 1 的 312G ≤ 337.92G（单测合规）与 §7.4 的 216G ≤ 220G（并发合规）分别对应各自场景，均满足 ≤88% 无 OOM 风险结论。
