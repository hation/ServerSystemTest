# 05 · 测试矩阵与分层模型（模板）

> 目的：定义整机测试的**三层执行模型**（L1 全量 / L2 抽样 / L3 外包）与**测试矩阵表模板**，配套能力评估三步走、软件可用性校验表、实施路径与常见困惑澄清。通用版（去业务化），供服务器整机测试项目套用。

> 变更记录：2026-11-13 新建（由 memory-tests 18 号 17 项矩阵 + L1/L2/L3 三层执行模型泛化为整机矩阵模板）

## 1. 三层执行模型

验收测试体系 = **测试矩阵**（测试项按客户标准定），按三层执行：

| 层 | 覆盖项 | 规模 | 当前状态 |
| --- | --- | --- | --- |
| **L1 全量**（每台必测） | 识别建档、全量压测、健康检查、稳定性 | 每台都做 | 按矩阵标注（软件项可测；目检/电性需仪表） |
| **L2 抽样**（每批抽 N 台） | 断电循环、老化、多平台兼容等 | 每批抽 N 台【示例：每 100 台抽 3–5 台】 | 按矩阵标注（多数可测，个别待确认平台） |
| **L3 外包**（工程样件） | 电压裕量、时序/眼图、高低温、湿热、ESD、振动、冲击、弯曲等 | 每来源类别送 1–3 件 | **当前全部不能测（无硬件）**，见 §2 标注 |

**验收结论 = L1 全量 0 失败 + L2 抽样通过 + L3 样件报告合格**，三者共同构成，缺一不可。

> ⚠️ 凡涉及硬件的项一律标注「当前不能测」：硬件没到位 = 该项当前不能测；需要什么硬件、能解决什么问题按矩阵与采购清单定（L3 类高价测量设备建议直接外包，一次送检在同一家实验室做齐）。

## 3. 能力评估三步走（软件项先确认能用）

> 原则：凡是软件项，先校验工具是否可用；不可用的按校验表做配置/安装。三步走：

| 步骤 | 脚本（占位，名称按新项目定） | 做什么 | 输出 | 失败处理 |
| --- | --- | --- | --- | --- |
| ① 环境自检 | `check_env.ps1` | 内置工具全检：PowerShell 版本、关键脚本齐全、内置工具（ipmitool / Memtest86+ / Prime95 / fio / smartctl / iperf 等【示例】）、配置模板 | 全部 OK 即可继续；逐项输出 | 有失败项按部署/离线手册修复 |
| ② 带外链路自检 | `diag_oob.ps1` | 带外（BMC/串口）连通性四步：基础信息 / 状态 / 传感器 / 控制台短探测 | 四步无 Error 即链路 OK | 失败按带外排查方案 |
| ③ 能力评估 | `assess_capability.ps1` | 按测试矩阵逐项给出「可测 / 需带外 / 需硬件 / 外包」 | `<机器名>-cap.csv` + 评估报告（落盘可追溯） | 重点确认：ECC 平台、电源控制、多平台项 |

> ⚠️ **带内项（CPU/内存/磁盘/网络等）读的是「运行脚本那台机器」**——要评估**被测机**，必须在被测机本机跑评估脚本（占位命令：`assess_capability.ps1 -Local -MachineName <被测机>`）；在编排机（PC）上跑只会读到编排机自身。带外项（断电/测温/串口）在编排机确认即可。**评估被测机须在机内跑**。

## 4. 软件可用性校验表模板（逐软件核对，缺什么配什么）

| 软件/工具 | 用途（覆盖项） | 怎么校验可用 | 不可用时怎么办 | 是否随包 |
| --- | --- | --- | --- | --- |
| ipmitool | 带外/断电/测温（电源、散热、整机稳定性） | `check_env` 内置项；`ipmitool.exe -V` | 用随包内置版，免配置 | ✅ 内置【示例】 |
| Memtest86+ | 内存全地址覆盖（内存全项） | `check_env` 内置项；ISO 存在 | 内置，免下载 | ✅ 内置【示例】 |
| Prime95 | 系统级长压（CPU 满载、混插、整机稳定性） | `prime95.exe -t` 能启动 | 内置，免下载 | ✅ 内置【示例】 |
| fio | 磁盘读写性能（磁盘性能达标线） | `fio --version` | 随包或 apt/联网安装 | ✅ 内置【示例】 |
| smartctl | 磁盘健康与缺陷（磁盘健康/坏块） | `smartctl --version`；能读目标件 | 随包或安装 | ✅ 内置【示例】 |
| iperf | 网络带宽/丢包延迟（网络） | `iperf -v`；能起服务端/客户端 | 随包或安装 | ✅ 内置【示例】 |
| HWiNFO | 温度/电压监控（散热、整机稳定性） | 启动后能读到 DIMM/CPU 温度 | **未随包**：自行下载安装 | ❌ 未随包【示例】 |
| WHEA（Windows）/ mcelog、edac-utils（Linux） | ECC 未纠正错误监控（内存 ECC、整机稳定性） | Windows：事件查看器 → Microsoft-Windows-WHEA-Logger；Linux：`which mcelog`、`ls /sys/devices/system/edac` | Windows 系统自带；Linux 安装 + 确认内核 EDAC 驱动 | ✅ 系统自带 / ❌ 未随包【示例】 |

> 值均为**示例**，由新项目按工具清单落定；`✅ 内置/系统自带` = 离线包已含或系统原生，直接可用；`❌ 未随包` = 需自行下载安装或离线携带，**跑对应测试项前先配好**；被测机若是 Linux，提前用离线包备好对应工具。

## 5. 实施路径（怎么一步步做）

```
阶段 0 准备与校验  check_env.ps1 + diag_oob.ps1 + assess_capability.ps1（§3 三步走）
阶段 1 建档  每台贴唯一 ID → 识别脚本识别分类 → 批次清单                  [L1 建档类]
阶段 2 目检/电性  目检 + 规格/容量/频率核对（电性复检需仪表到位）            [L1 目检电性类]
阶段 3 全量压测  全地址覆盖（按来源分类定深度）+ 部件满载/混压长压          [L1 压测类]
阶段 4 抽样可靠  断电循环、老化、多平台兼容（并行）                        [L2 抽样类]
阶段 5 外包送检  L3 全项同一实验室做齐（每来源类别 1–3 件；无硬件=当前不能测） [L3]
阶段 6 汇总报告  逐台 PASS/WARN/FAIL 总表 + 抽样报告 + 外包报告 → 验收结论
```

详细步骤按场景选手册（占位）：单机验收（1 台）/ 批量全检 / 失败件隔离复测。

## 6. 常见困惑澄清（结构占位，示例）

| 困惑 | 澄清 |
| --- | --- |
| "是不是跑完全量压测就验收完了？" | **不是**。按三层结论：L1 全量 0 失败 + L2 抽样通过 + L3 样件报告合格，才算完整验收。 |
| "为什么标「当前不能测」？" | 涉及硬件的项一律标注：硬件没到位就不能测；L3 类要测 → 采购或外包送检。 |
| "软件项怎么确认能用？" | 按 §3 三步走 + §4 校验表逐项核对，缺的配好。 |
| "跑完一轮怎么没看到日志/结果？" | 结果只产生在**编排机**的 `results\`；且必须**先启动编排器（抓流）再引导被测机**，顺序反了等于白测（没有数据可评估）。 |
| "带内项怎么读被测机？" | 带内项读的是"运行脚本那台机器"——评估被测机必须在被测机本机跑（§3 ③）。 |
| "每批抽 N 台怎么抽？" | 按 §1 L2 抽样规则：每批抽 N 台【示例：每 100 台抽 3–5 台】，抽样数由客户标准定。 |
| "命令行参数太多记不住？" | 常用默认参数下沉到配置文件，命令行显式参数优先；改配置即生效（占位）。 |
