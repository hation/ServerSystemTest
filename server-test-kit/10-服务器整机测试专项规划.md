## 1. 被测对象与范围

**被测对象 = 服务器整机**（单台成机验收，非单部件）。

覆盖 **7 类部件/维度**，每类的范围与关注点如下：

| # | 部件/维度 | 范围与关注点 |
| --- | --- | --- |
| 1 | CPU | 识别与配置核对、满载稳定性、温度上限 |
| 2 | 内存 | SPD 识别建档、全地址读写覆盖、混插压力、ECC |
| 3 | 磁盘 | SMART 健康与缺陷、坏块扫描、读写性能达标线 |
| 4 | 网络 | 连通性、带宽、丢包/延迟 |
| 5 | 电源 | 上电掉电循环、初始化稳定性（带外控制） |
| 6 | 散热 | 全程温度监控（CPU/DIMM/环境）、风扇状态 |
| 7 | 整机稳定性 | 系统级混压（多部件同跑）+ 未纠正错误/系统事件监控 |

> 范围口径：整机验收 = 各部件逐项过关 + 整机混压稳定，最终按 §5 三层（L1/L2/L3）给出验收结论。

## 2. 部件 × 标准工具选型表（示例）

> 列 = 部件 / 标准工具 / 用途 / 平台。**以下全部为「标准工具选型示例」**，新项目按目标平台与客户要求落定；带外编排链路（BMC/SOL）参考 memory-tests 的 SOL 全自动方案。

| 部件 | 标准工具（示例） | 用途 | 平台 |
| --- | --- | --- | --- |
| CPU | Prime95（备选：stress-ng / wprime） | CPU 满载稳定性、全核压力长压 | Windows / Linux |
| 内存 | **Memtest86+**（SOL 编排，参考 memory-tests）、memtester | 全地址读写覆盖、快速内存自检 | 引导介质（SOL/USB/EFI）/ Linux |
| 磁盘 | smartctl / fio / badblocks | SMART 健康与缺陷、读写性能达标线、坏块扫描 | Linux（smartctl 亦可 Windows） |
| 网络 | iperf / ping | 双向带宽、丢包/延迟统计 | Windows / Linux |
| 带外管理 | **ipmitool / BMC / SOL**（含 BIOS 串口重定向 115200 配置） | 断电循环、测温、串口抓流（全自动编排前提） | 编排机（Windows）+ 被测机 BMC |
| 监控 | HWiNFO / IPMI sdr / WHEA | 温度/电压监控、未纠正错误记录 | Windows（HWiNFO/WHEA）、BMC（sdr） |
| Linux ECC | mcelog / edac-utils / rasdaemon | ECC 未纠正错误监控 | Linux |
| 服务器识别 | dmidecode / lscpu / wmic | 识别型号/SN/CPU/内存/磁盘/固件版本 | Linux / Windows |

> 选型原则（来自两项目实证）：**先调研底层标准工具，能用的标准工具先选定型，不自己造轮子**（结论可审计可解释）；编排器只做"引导 + 抓流 + 判读"，重活交给标准工具。

## 3. 被测对象识别与建档

### 3.1 识别什么（基本信息）

| 项 | 说明 | 带内命令示例 |
| --- | --- | --- |
| 型号（厂商/型号） | 整机身份 | `wmic csproduct get name,vendor` / `dmidecode -t system` |
| SN / 资产号 | 唯一键（见 3.2） | `wmic csproduct get identifyingnumber` / `dmidecode -t system \| grep Serial` |
| CPU | 型号/核数/线程/频率 | `wmic cpu get name` / `lscpu` |
| 内存 | 容量/条数/厂商 | `wmic memorychip get ...` / `dmidecode -t memory` |
| 磁盘 | 型号/容量/SN/盘位 | `smartctl -a` / `lsblk` |
| 固件版本 | BIOS/BMC 版本 | `wmic bios get smbiosbiosversion` / `dmidecode -t bios`；BMC 网页/IPMI |

### 3.2 唯一键定义

**唯一键 = 资产号或 SN**（两者取一，优先资产号；无则兜底 `Asset_<n>`）。唯一键决定历史库归并、跨批次追踪、报告汇总（参考 disk-tests 29 号 §4.2 第 1 问）。

### 3.3 建档与防调包

- 建档：识别数据写入**批次清单**（`manifest.csv`），每台一行，含唯一键 + 识别字段 + 预期清单匹配结果。
- **防调包**：识别数据与**预期清单比对**（型号/SN/部件清单逐项核对），不一致即标记异常，不进入压测流程（参考 memory-tests 第 1/2 项「识别建档、防调包」）。

### 3.4 带内 / 带外两种识别路径

| 路径 | 怎么做 | 适用 |
| --- | --- | --- |
| **带内** | 在**服务器本机**跑识别命令（wmic/lscpu/dmidecode，见 3.1） | 服务器已装 OS、可登录 |
| **带外** | BMC 管理网页或 `ipmitool` 读身份信息（BMC 独立于 OS，服务器没装 OS 也能读） | 未装 OS / 批量快速核对 |

> 参考：memory-tests `docs/13-服务器信息识别指南.md`（纯小白向的识别步骤，可直接套用）。带内识别脚本须**在被测机本机运行**（带内项读的是运行脚本那台机器，见 §6）。

## 5. 分层执行落地路径

### 5.1 三层执行模型（引用 05 号）

| 层 | 覆盖 | 规模（示例） | 落地要点 |
| --- | --- | --- | --- |
| **L1 全量** | 识别建档、目检、全量压测、健康检查、整机稳定性 | 每台必测 | 软件项编排器全自动；目检人工；电性需仪表 |
| **L2 抽样** | 断电循环、老化（ORT）、多平台兼容等 | 每批抽 N 台【示例：每 100 台抽 3–5 台，按客户定】 | 并行开展，多数软件可测 |
| **L3 外包** | 电压裕量、时序/眼图、高低温、湿热、ESD、振动、冲击等 | 每来源类别送 1–3 台 | **无硬件 = 当前不能测**，一次送检同一实验室做齐 |

**验收结论 = L1 全量 0 失败 + L2 抽样通过 + L3 样件报告合格**，三者缺一不可（05 号 §1）。

### 5.2 实施路径（阶段 0–6，各阶段引用对应模板文档）

```
阶段 0 准备与校验  check_env.ps1 + diag_oob.ps1 + assess_capability.ps1   ← 05 号 §3 三步走
阶段 1 建档        识别 + 预期清单比对 → 批次清单（唯一键）                 ← 02-批量检测SOP（识别建档）
阶段 2 目检/电性    目检 + 规格核对（电性复检需仪表到位）                   ← 04-单实体专项分析SOP / 目检清单
阶段 3 全量压测     CPU/内存/磁盘/网络 全量 + 整机混压长压（编排器全自动）   ← docs-template 01-测试方案 + XX-使用手册
阶段 4 抽样可靠     断电循环、老化、多平台兼容（并行）                      ← 05 号矩阵 L2 项
阶段 5 外包送检     L3 全项同一实验室做齐（无硬件 = 当前不能测）             ← 05 号 §2 矩阵 + 采购/外包清单
阶段 6 汇总报告     逐台 PASS/WARN/FAIL 总表 + 抽样报告 + 外包报告 → 验收结论 ← 08-报告与汇总表规则 + 03-AI评测提示词
```

> 失败件处理：单台隔离 → 换深度档复测 → 确认失效后按判据定值表给结论（参考 memory-tests 单根隔离做法）。

## 6. 能力评估三步走（软件项先确认能用）

> 原则：凡是软件项，先校验工具可用；不可用的按 §8 校验表做配置/安装。三步走：

| 步骤 | 脚本（占位） | 做什么 | 输出 | 失败处理 |
| --- | --- | --- | --- | --- |
| ① 环境自检 | `check_env.ps1` | **内置工具全检 6 项（示例）**：① PowerShell 5.1+ ② 关键脚本齐全 ③ 内置 ipmitool（含 DLL+版本）④ Memtest86+ ISO ⑤ 配置模板 ⑥ SQLite 历史库（可选，需 Python） | 逐项输出，全部 OK 即可继续 | 有失败项按部署手册/离线手册修复 |
| ② 带外链路自检 | `diag_oob.ps1` | 带外连通性**四步**：`mc info`（基础信息）/ `chassis status`（机箱状态）/ `sdr elist`（传感器）/ `sol activate`（串口控制台短探测） | 四步无 Error 即链路 OK | 失败按带外排查方案 |
| ③ 能力评估 | `assess_capability.ps1` | 按测试矩阵逐项输出「**可测 / 需带外 / 需硬件 / 外包**」 | `<机器名>-cap.csv` + 评估报告（落盘可追溯） | 重点确认：ECC 平台、电源控制、多平台项 |

> ⚠️ **带内项（CPU/内存/磁盘/网络/识别等）读的是「运行脚本那台机器」**——要评估**被测服务器**，必须在**服务器本机**跑评估脚本（占位命令：`assess_capability.ps1 -Local -MachineName <被测机>`）；在编排机（PC）上跑只会读到编排机自身。带外项（断电/测温/SOL）在编排机确认即可。**评估被测服务器必须在机内跑**。

## 7. 结果产生位置（重要约定，先看这里）

- **压测结果（原始日志 / 报告 / 总表）只产生在「运行编排器那台机器」**——被测服务器只跑测试（如 Memtest 等引导介质测试），把日志打到串口（BMC SOL），**不写任何 results 文件**（参考 memory-tests 18 号 §5.5）。
- **必须先启动编排器（开 SOL 抓流），再引导被测机**——顺序反了会错过日志：先引导跑完、编排器才启动，SOL 流没人接，**等于白测**。
- **没跑编排器 = 没有数据 = 无法评估**。评估入口全部在编排机的 `results\` 下：

| 文件 | 看什么 |
| --- | --- |
| `results\raw\<批次>.mtlog.txt`（或等价原始日志） | 原始事件：`ev=start` / `ev=pass_end ... errors=0` / `ev=done passes=N status=pass` |
| `results\reports\<批次>-report.csv` | 逐台结果：错误数 0、状态 pass 即通过 |
| `results\master_manifest.csv` | 累计总表（跨批次对比，按唯一键追踪） |

- 引导方式提醒（参考 memory-tests 四种引导）：**BMC 虚拟介质 = 全自动**（远程挂载、SOL 无人值守，批量推荐）；**Serial = 完全离线**；**USB/Ventoy = 半自动**（人工插拔）；**EFI = 一次性引导**。

## 9. 常见困惑澄清（结构占位，示例）

| 困惑 | 澄清 |
| --- | --- |
| "跑完全量压测就算验收完了？" | **不是**。按三层结论：L1 全量 0 失败 + L2 抽样通过 + L3 外包报告合格，三者缺一不可（§5.1）。 |
| "判据数值（如 95°C）能直接抄吗？" | **不能**。本规划全部判据数值为【示例，按客户定值】；正式判据填入 §4 判据定值表，来源写清（客户规格/订单/行业标准）。 |
| "为什么标「当前不能测」？" | 涉及硬件的项一律标注：硬件没到位 = 当前不能测；L3 类要测 → 采购或外包送检（§5.1）。 |
| "带内项怎么读被测服务器？" | 带内项读的是"运行脚本那台机器"——评估/识别被测服务器必须在**被测机本机**跑（§6 ③、§3.4）。 |
| "跑完一轮怎么没看到日志/结果？" | 结果只产生在**编排机**的 `results\`；且必须**先启动编排器（抓流）再引导被测机**，顺序反了等于白测（§7）。 |
| "工具名/脚本名怎么定？" | §2/§6/§8 均为**选型示例**（两项目实证过的通用做法），新项目按目标平台与客户要求落定，套用 docs-template 时替换占位符。 |
