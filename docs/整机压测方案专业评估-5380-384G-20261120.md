## 2. 朋友方案参数分解与严谨推导

### 2.1 CPU = 45：物理核全开 + SMT 补强 + 给 IO 留余量

**45 的两条独立推导路径（殊途同归）：**

- 路径 A：物理核全开 + SMT 补强 → 32 + 13 = **45**。
- 路径 B：逻辑线程 70% 口径 → round(64 × 70%) = round(44.8) = **45**。

**为什么留 19 个逻辑线程（64 − 45 = 19，≈30%）：**

- 14 路数据盘 + 1 路系统盘并发写盘时，内核需要 CPU 处理：块设备中断、页缓存回收（kswapd）、脏页写回（flusher 线程）、文件系统（XFS/ext4）元数据操作。IO 压测同样吃 CPU（fio 文档建议 numjobs 对齐 vCPU 以最大化负载）。
- stress 的 `--cpu` worker 是纯 `sqrt()` 自旋进程（stress manpage：*"Spawn N workers spinning on sqrt()"*），属计算密集、无外部等待负载，占用率接近 100%/worker。45 个 worker 会把 32 个物理核压满，13 个 SMT 线程作为补强，同时留下 19 个逻辑线程给 IO 栈与系统，避免 CPU 全满时内核 IO 处理被饿死。

**SMT 对纯计算负载的增益（关键决策依据）：**

- Intel 官方白皮书（*Hyper-Threading Technology: Impact on Compute-Intensive Workloads*, Magro et al.）实测 9 个计算密集型应用 + 6 个测试内核：SMT 加速比 1.00~1.28；其中 **dgemm（纯矩阵乘、高 ILP）SMT 加速比 = 1.00（零增益）**，有限元 A1 = 1.05（+5%）。
- 现代架构（AMD Zen 5 EPYC 9755，Phoronix 实测）SMT 增益高度负载相关：Coremark +30%，而 ClickHouse 上 SMT 反而略差。
- 海光 C86 5380 基于 Zen 1（Dhyana）架构，SMT 分时复用效率低于 Zen 5；对 `sqrt()` 自旋这类纯计算负载，**SMT 增益预计 ≤ 5~10%**（以 dgemm=1.00、A1=1.05 为上下界参考）。

**三档取舍对比：**

| 口径 | 算式 | 特点 |
|---|---|---|
| 64 全开 | 32 物理核 + 32 SMT | 纯计算负载下 SMT 线程仅贡献 ≤5~10% 吞吐，却与 IO/内核抢占执行单元、增加调度与功耗；不给 IO 留余量 |
| 45（朋友） | 32 + 13 | 物理核 100% 满载，SMT 补强 13 个线程（吃满 SMT 那 ≤5~10% 收益的主要部分），留 19 线程给 14 路 IO + 系统 |
| 32 纯物理核 | 32 + 0 | 放弃 SMT 全部潜在收益；纯 CPU 压测口径，整机场景偏保守 |

**结论：45 是"CPU+内存+14 盘 IO 并发"整机压测场景下物理核利用率与 IO 余量的合理折中，参数本身无风险。**

### 2.2 VM = 12：内存条根数

- 12 = 本机 DIMM 根数（12 × 32G）。每根内存条 1 个 vm worker，均匀覆盖全部内存通道与全部内存条——与脚本口径一致（脚本：`--vm` 默认按 DIMM 根数探测，`--vm` 须等于 DIMM 根数才走单根容量规则）。

### 2.3 --vm-bytes 24G：单条 32G − 8G 预留；总量 75%

- 单 worker：24 = 32 − 8（单条 32G 留 8G 给系统/页缓存）。脚本公式为 32 − max(6, 32/8) = 32 − 6 = **26G**，朋友的 24G 比脚本口径**再保守 2G**。
- 总量：12 × 24 = **288G**；288 / 384 = **75%**（标称口径）；288 / 372 ≈ **77.4%**（MemTotal 估算口径）。
- **70~80% 是业界内存压测目标区间**，依据：
  - 反向口径 1：OOM 调试经验规则——峰值负载时保持 `MemAvailable` ≥ MemTotal 的 10~15%（kernel-internals.org）；
  - 反向口径 2：运维惯例"20% rule"——预留约 20% RAM 给 OS 与关键服务（dohost）；
  - 脚本自身口径：MEM_TARGET_PCT=82%、MEM_MAX_PCT=88%（模块总容量上限）、MEM_TOTAL_MAX_PCT=92%（MemTotal 上限）。75% 落在脚本 82% 目标线以内。
- **OOM 风险口径（Linux 页缓存可回收机制）**：OOM killer 只在"内核无法回收足够内存"时才触发（kernel.org mm/concepts）。页缓存/脏页是**可回收内存**——脏页达到 dirty_background_ratio（默认 10%）时后台 flusher 异步写回、达到 dirty_ratio（默认 20%）时写进程同步参与写回（kernel.org sysctl/vm）。压测内存占用 75% 时，剩余空间几乎全部作为可回收页缓存兜底 14 路写盘；页缓存空间不足只会加快写回、抬高 IO 延迟，**不会直接导致 OOM**。
- **专业关键点（朋友裸命令 vs 脚本的差异）**：经典 stress 的 `--vm` 默认行为是 *"Spawn N workers spinning on malloc()/free()"*，`--vm-keep` 才是 *"Redirty memory instead of freeing and reallocating"*（stress manpage）。**朋友裸命令未带 `--vm-keep`，288G 是"分配→touch→释放→再分配"的间歇占用，并非持续常驻**——内存压测强度低于名义值；脚本 mem/combo 固定追加 `--vm-keep`（常驻）。

### 2.4 整机账目（朋友方案，加 --vm-keep 常驻口径）

| 项 | 算式 | 结果 |
|---|---|---|
| 压测常驻 | 12 × 24 | 288G |
| MemTotal（估算） | 384 × 0.969 | ≈372G |
| 系统占用（内核+服务） | 估算 | 4~8G |
| 页缓存可用空间 | 372 − 288 − 4~8 | **≈76~80G** |
| 14 盘写盘页缓存峰值需求 | 14 × 10G（hdd-bytes 默认） | 140G（峰值，瞬时） |

- 页缓存峰值需求（140G）> 可用页缓存空间（76~80G）：稳态下写回频率升高、IO 吞吐波动，属预期现象；因 12×8TB SATA SSD + 2×NVMe 刷盘快（NVMe 顺序写 GB/s 级、SATA SSD 数百 MB/s 级），140G 脏页可在数十秒内刷完，**不构成 OOM 风险**。
- 边界：若 MemTotal 实测偏低（<368G）或机器上并存大内存业务，页缓存空间进一步压缩，建议降档（见 §6）。

## 3. 脚本算法精确计算（代入公式，逐步算式）

公式出处：`stress-lib-common.sh`（cpu_workers_auto / smt_tpc / mem_plan）与 `stress-lib-commands.sh`（内存计划、三道上限、逐 GiB 下调），参数默认值见 `stress-test.sh`（CPU_MAX_PCT=78、MEM_TARGET_PCT=82、MEM_MAX_PCT=88、MEM_TOTAL_MAX_PCT=92、DISK_CACHE_FACTOR_PCT=120、DISK_CACHE_MIN_G=8）。

### 3.1 CPU worker 数

脚本公式：`max(1, round(逻辑线程 × 25/32))`，逻辑线程 = 物理核 × 每核线程数（SMT 探测，未知默认 2）；实现为 bash 整数除法 `w = (logical×25 + 16) / 32`。

- **SMT 开**（本机默认）：logical = 32 × 2 = 64
  - w = (64 × 25 + 16) / 32 = 1616 / 32 = 50.5 → bash 截断 = **50**
- **SMT 关**：logical = 32 × 1 = 32
  - w = (32 × 25 + 16) / 32 = 816 / 32 = 25.5 → bash 截断 = **25**
- 兜底路径（物理核识别失败）：round(64 × 78%) = (64×78+50)/100 = 5042/100 = **50**（与主路径一致）

**脚本 CPU=50（占 64 线程的 78.1%），比朋友 45 更激进 5 个线程；脚本口径不为 IO 专门留余量。**

### 3.2 内存：无盘流（mem 模式 / combo peer=0，仅 CPU+内存）

- worker 数：vm = DIMM 根数 = **12**（显式 `--vm 12` 与探测一致）
- 单 worker（单根规则）：单条 = 32G → reserve = max(32/8, 6) = max(4, 6) = **6G** → per = 32 − 6 = **26G**
- 总量：12 × 26 = **312G**（占 MemTotal 估算 372G 的 83.9%；标称 81.25%）
- 三道上限：
  - cap_module = 单条 32 × 12 根 × 88% = 384 × 0.88 = 337.92 → **337G**（精确：393216×88/100 = 346030 MB → /1024 = 337G）
  - cap_mem = MemTotal × 92% ≈ 372 × 0.92 = 342.24 → **342G**（估算 MemTotal；以实测为准）
  - cap_disk：无盘流（disk_streams_eff=0）→ **不生效**
  - 上限 = min(337, 342) = **337G**
- 312G ≤ 337G → **不裁剪，最终 12 × 26G = 312G**

### 3.3 内存：有盘流（all/full 整机，peer = 14 + 1 = 15，hdd-bytes 默认 10G）

- 盘流数：数据盘 14 + 系统盘 1（--sysdisk-only）= 15；--peer-disks 15 声明对端并发盘流 → disk_streams_eff = max(15, 15) = **15**
- 盘流页缓存预留：disk_need = 15 × 10G × 1.2 + 8G = 180 + 8 = **188G**
- cap_disk = MemTotal − disk_need ≈ 372 − 188 = **184G**（估算 MemTotal）
- 三道上限 = min(337, 342, 184) = **184G**
- 逐 GiB 下调：26G × 12 = 312G > 184G → 需求 per × 12 ≤ 184 → per ≤ 15.33 → **per = 15G**（15×12 = 180 ≤ 184 ✓；16×12 = 192 > 184 ✗）
- **最终：12 × 15G = 180G**（从 312G 裁剪 132G，每 worker 下调 11G）
- 灵敏度（以实测 MemTotal 为准）：MemTotal ∈ [368, 380]G 时 cap_disk ∈ [180, 192]G，per 均取 15G（180 ≤ cap_disk）→ **15G/180G 结论稳健**；仅当 MemTotal ≥ 384G 才可能升到 16G。

### 3.4 显式 --vm-bytes 24G（朋友裸命令，脚本口径下的处理）

- need = 12 × 24G = 24576 MB × 12 = 294912 MB = **288G**
- 上限 = min(337, 342, 184) = **184G**（有盘流口径）
- 288G > 184G → `bytes_from_preset=0` → **脚本只告警不裁剪**（"内存需求 288G 超过分配上限 184G，可能触发 OOM；按显式参数继续"）
- 说明：脚本 full 模式默认按**朋友规则**推导（CPU≈70%、vm-bytes=脚本单根推导 26G）并作为显式参数下发，走的是与显式设置相同的告警路径——显式参数优先、原样保留、只告警不裁剪；显式设置 `FULL_VMBYTES=24G`（oneclick.sh）时用所给值，同样只告警不裁剪。仅当朋友规则推导失败（硬件探测不可用）回退脚本自动推导路径（不传 --vm-bytes）时，才会裁剪到 12×15G=180G。

## 5. 结论：能否这么用？

**判断逻辑：先明确压测目的，再选参数口径。**

**场景 A：整机压测强度优先（目的即"CPU+内存+全盘并发，越狠越好"）→ 可以，边界条件如下：**

1. **CPU 45：完全可用，无风险。** 32 物理核满载 + SMT 补强 + 留 19 线程给 IO，是整机场景的正确取舍（§2.1）。
2. **内存 12×24G=288G：可用，但必须理解两点边界：**
   - **必须加 `--vm-keep`** 才实现持续常驻 288G；朋友裸命令是 malloc/free 循环，实际内存强度达不到名义 75%（若目的是"稳定压满内存"，这是参数缺陷；若只是"带内存负载"，反而更安全）。
   - 常驻 288G 后，页缓存空间仅剩 ~76~80G（MemTotal 估算 372G − 288G − 系统 4~8G），14 盘写盘（峰值 140G 页缓存需求）会造成**高写回频率与 IO 波动**，属预期现象，不触发 OOM（页缓存可回收 + SSD/NVMe 刷盘快）；**以 MemTotal 实测 ≥ ~372G 为前提**，且全程监控 `MemAvailable` 与 dmesg OOM 日志（§6）。
3. `--timeout 10h`：stress 支持 `h` 后缀（manpage：数字可带 s/m/h/d/y 时间后缀），合法。

**场景 B：安全优先 / 首次跑 / 有并存业务 → 脚本方案（combo 自动推导，12×15G=180G 常驻 + 188G 盘流预留 + 自动监控落盘），OOM 风险最低。**

**场景 C（推荐混合）：脚本 full 模式。** 显式设置 FULL_CPU=45 / FULL_VM=12 / FULL_VMBYTES=24G（朋友方案）时，等于"朋友方案 + --vm-keep 常驻 + 每盘独立 hdd 进程 + 系统盘 + 监控与落盘 + peer=15 声明"，并把 24G 超 184G 上限的告警落在日志里；强度不降、安全设施齐备（未显式设置则默认按朋友规则推导 45/12/26G，同为高强度、同样不裁剪）。想更保守用 `FULL_VMBYTES=20G` 降档（见 §6）。

**一句话：参数口径（45/12/24G）本身专业、可用；唯一硬伤是裸命令缺 `--vm-keep` 导致内存不常驻，以及 288G 常驻下页缓存余量偏紧需监控——脚本 full 模式默认按朋友规则推导（45/12/26G，脚本单根推导口径）即可补齐这两点，也可显式设置 45/12/24G 同朋友方案（推导失败才回退脚本自动推导）。**

## 6. 使用建议

1. **hdd-bytes 建议**：默认 10G 对 SSD/NVMe 合理（刷盘快，页缓存需求为瞬时峰值）；若现场 IO 波动明显可降 5G（盘流预留从 188G 减半为 98G，页缓存压力骤降）。
2. **MemTotal 实测核对**：`grep MemTotal /proc/meminfo`（预计 368~380 GiB）。报告 §3 所有 cap_mem/cap_disk 数值基于 372G 估算，实测后重算：cap_disk = MemTotal − 188G，per = 满足 12×per ≤ cap_disk 的最大整数。
3. **现场监控**：
   - `free -h`：盯 `MemAvailable`（保持 ≥ 10~15% MemTotal，即 ≥ ~40~55G）；
   - `sar -r -B`：内存与页交换/IO 指标；
   - `dmesg -T | grep -iE 'oom|out of memory|killed process'`：OOM killer 现场（脚本 monitor-loop 已内置该正则，30s 间隔自动落盘）。
4. **抖动降档路径**：写盘 IO 抖动或 MemAvailable 过低时，`FULL_VMBYTES=20G` → 12×20=240G（标称 62.5% / MemTotal 估算 64.5%），页缓存空间回到 ~124~128G；极端可 `16G` → 192G（≈51.6%）。
5. **与脚本 full 模式衔接**：`bash oneclick.sh full`（菜单 2）默认按**朋友规则**推导（CPU≈round(逻辑线程×70%)、VM=DIMM 根数、vm-bytes=脚本单根推导 单条容量−max(单条/8,6G)，如 45/12/26G，推导值显式下发不裁剪）；显式设置 `FULL_CPU/FULL_VM/FULL_VMBYTES` 环境变量时即为朋友参数或自定义值（oneclick.sh 第 53~58 行）。推导/显式的 `--vm-bytes`（如 26G 或 24G）在脚本口径下会告警"超分配上限 184G"但不裁剪——该告警是脚本按"有盘流预留 188G"的保守口径给出，312G/288G 常驻不必然 OOM（页缓存可回收），理解告警含义并配合监控即可；若希望脚本自动裁剪到安全值，则仅当 full 朋友规则推导失败回退 combo 自动推导（不传 --vm-bytes，12×15G=180G）时才会发生。
